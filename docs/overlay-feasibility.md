> 分支：`experiment/native-overlay-camera`　｜　日期：2026-10-23
> 目的：重新验证 AGENTS.md §13 里那句「安卓系统级悬浮窗拿不到系统相机画面，实际不成立」。
> 相关代码：`android/app/src/main/java/cn/photocoach/app/probe/`（独立验证入口，不影响主壳）

## 0. 结论先行

| 路线 | 能读画面 | 能叠加 | 画质 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 自建 Camera2 预览 + 原生叠加** | ✅ | ✅ | 接近原相机（缺厂商多帧算法） | **可行，推荐** |
| **B. 悬浮窗盖系统相机 + MediaProjection 读帧** | ⚠️ 取决于系统相机是否 `FLAG_SECURE` | ✅ | 原相机（真·上限） | **有条件可行，不建议作为主方案** |
| **C. 只用悬浮窗，不读画面** | ❌ | ✅ | 原相机 | 可行但价值低，只能当降级 |
| **D. AccessibilityService.takeScreenshot** | ⚠️ 有频率上限、secure 窗口直接报错 | ✅ | 原相机 | **不成立** |

**推荐 A**：自己写相机预览（Camera2 平台 API，零依赖），指导层画在自己的预览上。

**为什么不是 B**：它把「能不能用」押在一件我们控制不了的事上——系统相机 App 有没有给预览窗口打
`FLAG_SECURE`。而且 Android 14 起每次开启录屏都要用户点一次系统授权弹窗，等于每次拍照前多一道门。

**最大的坑**：A 的画质上限不是「传感器上限」，是「第三方能拿到的上限」——多帧 HDR、夜景合成、
高像素模式这些是厂商相机 App 的私有实现，第三方拿不到（部分能通过 Camera2 Extension 拿到，见 §2.4）。

## 1. 先把 AGENTS.md 那句话拆开

原文（§13 待办最后一条）：

> ② 把指导层做成原生浮层盖在系统相机上（安卓系统级悬浮窗拿不到系统相机画面，实际不成立）。

这句话把两件事混成了一件：

| 拆开后的命题 | 对不对 | 依据 |
| --- | --- | --- |
| **读不到系统相机的预览帧** | ✅ 对 | 没有任何公开 API 能让第三方 App 拿到另一个 App 的相机流。相机是独占资源，Camera2 打开会直接失败 |
| **不能在上面画东西** | ❌ 错 | 悬浮窗（`TYPE_APPLICATION_OVERLAY`）在 WindowManager 里就是 Z 序更高的普通窗口，系统相机只是一个普通 Activity 窗口，没有任何机制阻止别的窗口盖在它上面 |

所以准确的表述是：**能画，但画上去的剪影不知道该画在哪**——因为没有画面就没有姿势检测，
剪影只能固定在屏幕某个位置，套不住真人。

而本项目 §1 写明「剪影是参考线，不是装饰，必须能准确套住真人」。**这条产品红线直接否掉了 C 路线**
（只有悬浮窗、不读画面）。这就是为什么「能画」这个技术事实并不自动等于「这条路能用」。

## 2. 逐条路线

### 2.1 悬浮窗（`SYSTEM_ALERT_WINDOW`）

**机制**：`WindowManager.addView()` + `TYPE_APPLICATION_OVERLAY`（API 26+；API 24/25 用
`TYPE_PHONE`）。加 `FLAG_NOT_TOUCHABLE` 后完全不拦截触摸，底下的相机快门照常能按。

**权限**：`SYSTEM_ALERT_WINDOW` 是特殊权限，不是运行时权限，必须跳
`Settings.ACTION_MANAGE_OVERLAY_PERMISSION` 让用户手动打开。

**国产 ROM 实际难度**（按经验，非官方文档，需要真机复核）：

| ROM | 表现 |
| --- | --- |
| 原生 / Pixel | 设置页一开即用，稳定 |
| 小米 / HyperOS | 设置里有「显示悬浮窗」，多数机型可用；但「后台弹出界面」是另一个开关，容易漏 |
| 华为 / HarmonyOS | 有独立「悬浮窗」权限页，部分机型还要在「应用启动管理」里允许后台活动 |
| OPPO / vivo | 权限页藏得深（应用管理 → 权限管理 → 悬浮窗），且部分机型会定期回收 |

结论：**能拿到，但拿到的比例不会是 100%**，而且用户要在设置里翻两三层。这个摩擦对本产品的
目标用户（帮人拍照的普通人）不算小。

**实际价值评估**：如果不读画面，浮层能做的事只剩三件——

1. 三分构图网格 / 水平仪 → 有用，但网页端已经有了，用户按快门时并不在网页上
2. 姿势文字提示（"手抬高一点"）→ 有用，但要说清"抬多少"就得看画面
3. 固定位置的剪影轮廓 → **几乎无用**。人站远站近、镜头推前推后，剪影位置全错

所以单靠悬浮窗，解决不了「拍的时候看不到指导」这个原始痛点。它只能算半个答案。

### 2.2 MediaProjection（录屏）

这是**唯一**可能同时做到「原相机画质 + 实时检测 + 叠加」的路径：录屏拿到含相机预览的画面 →
喂给姿势检测 → 结果画在悬浮窗上。

**关键疑问：系统相机预览是不是 `FLAG_SECURE`？**

官方对 `FLAG_SECURE` 的定义（`WindowManager.LayoutParams`）：

> Window flag: treat the content of the window as secure, **preventing it from appearing in
> screenshots or from being viewed on non-secure displays**.

也就是说，只要系统相机 App 给自己的预览窗口加了这个 flag，MediaProjection 录到的就是黑块。

**诚实的回答：这件事没有统一的官方答案，取决于厂商的相机 App，必须真机实测。**

- 原生 AOSP / Pixel 的相机预览一般**不是** secure，录屏能拍到（所以市面上有大量"录屏拍相机"的
  教程和 App）；
- 国产 ROM 的相机 App 出于防诈骗 / 防翻拍考虑，**部分机型确实会打 `FLAG_SECURE`**，具体哪些型号、
  哪个系统版本，没有公开清单，网上说法互相矛盾。

我没有设备，无法给出结论。所以原型里专门做了探针（见 §5 按钮 2）：它把屏幕录下来，
每 350ms 采样中间区域的平均亮度，直接显示「有画面 / 疑似全黑」。**跑一次就知道你这台机器行不行。**

**官方硬约束（这些是确定的，比 FLAG_SECURE 更致命）**：

| 约束 | 出处 | 影响 |
| --- | --- | --- |
| 每次会话前必须征得用户同意 | MediaProjection 官方文档 | **每拍一次照就要点一次系统弹窗** |
| 令牌一次性，`createVirtualDisplay()` 每个实例只能调一次 | 同上（Android 14 起违反抛 `SecurityException`） | 不能"授权一次用一天" |
| targetSdk 34 必须有 `FOREGROUND_SERVICE_MEDIA_PROJECTION` + `mediaProjection` 类型前台服务 | 同上 | 常驻通知栏 |
| Android 15 QPR1+ 状态栏常驻提示条，锁屏即停 | 同上 | 用户随时看到"正在录屏"，心理压力大 |

**自己录自己**：浮层会被一起录进去，检测器看到的是自己画的剪影，形成反馈环。
解法是给浮层窗口加 `FLAG_SECURE`——它就不会出现在录制结果里。原型里已经这么做了。

**延迟与功耗（量级估算，未实测）**：

- 屏幕捕获本身 1~2 帧（33~66ms）
- 降采样 + 姿势推理 30~80ms（lite 模型，中端机）
- 叠加层渲染 1 帧
- 合计 **100~200ms 量级**。姿势指导不需要低延迟，这个数字可以接受
- 功耗：相机 + 录屏 + 持续推理三份负载叠加，比单开相机明显更热。长时间拍会烫

**结论：有条件可行**。条件是「你的目标机型上系统相机预览不是 `FLAG_SECURE`」，而这个条件
我们没法在发版前保证——用户换一台手机就可能失效。

### 2.3 AccessibilityService.takeScreenshot

看着很美：无障碍服务能截屏，还能叠 `TYPE_ACCESSIBILITY_OVERLAY`。实际四条死因：

| 死因 | 依据 |
| --- | --- |
| **有频率上限** | 官方错误码 `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT`（API 30）："too little time has elapsed since the last screenshot"。接口语义是「截一张图」而不是「持续取流」，两次截图之间必须隔开一段时间；无论阈值具体是多少，都远达不到 15fps 的姿势检测需求 |
| **secure 窗口直接失败** | `ERROR_TAKE_SCREENSHOT_SECURE_WINDOW`（API 34）："the window contains secure content"。系统相机一旦是 secure，连黑图都拿不到，直接报错 |
| **权限存活率低** | 无障碍是"高危权限"，国产 ROM 会定期清理、开机不自动恢复、部分机型限制自启动。用户还得进设置 → 无障碍 → 已下载的服务里手动开 |
| **Google Play 政策** | 无障碍 API 只允许用于「帮助残障用户使用设备」。拿它做截图做姿势检测，属于明确的滥用，上架会被拒/下架 |

**结论：不成立**。技术上被频率卡死，合规上被政策卡死。

### 2.4 Camera2 / CameraX 自建预览

**能拿到什么**（平台 API，零依赖）：

- 全分辨率 JPEG：`StreamConfigurationMap.getOutputSizes(ImageFormat.JPEG)` 里最大的那个，
  通常是传感器全尺寸（1200 万像素机就是 4000×3000）
- OIS 光学防抖：`LENS_OPTICAL_STABILIZATION_MODE`，硬件支持就默认生效
- 连续对焦、手动曝光、RAW
- 预览帧：`ImageReader` 拿 `YUV_420_888`，直接喂姿势检测

**拿不到什么**（这才是"和原相机的真实差距"）：

| 能力 | 第三方能否拿到 | 说明 |
| --- | --- | --- |
| 多帧 HDR / 夜景合成 | ❌ 基本拿不到 | Pixel 的 HDR+、各家夜景模式都是相机 App 内部管线，不对外 |
| 高像素模式（5000 万/1 亿） | ❌ | 通常只有系统相机 App 能开，第三方拿到的是合并后的 12MP |
| 人像虚化 / 美颜 | ⚠️ 部分 | 只能自己算，或走 Camera2 Extension |
| 厂商调色 / 影调 | ❌ | 私有 |
| **Camera2 Extension**（`CameraExtensionCharacteristics`，API 31+） | ✅ 部分 | `EXTENSION_HDR` / `EXTENSION_NIGHT` / `EXTENSION_BOKEH` / `EXTENSION_FACE_RETOUCH`，由厂商 HAL 实现，能力因机型而异，要先查 `getSupportedExtensions()` |
| 视频防抖 EIS | ✅ | `CONTROL_VIDEO_STABILIZATION_MODE`，但只作用于预览/录像，不作用于静态拍照 |

**关于「黑屏 1~2 秒」**：MainActivity 注释里说的那个黑屏，来源是 **WebView 的 `getUserMedia` 已经
占着相机**，要切到 Camera2 就得先停流、等系统释放、再打开。如果一开始就不用 WebView 拿摄像头
（独立 Activity 直接 Camera2），**这个黑屏不存在**，首帧预览通常在几百毫秒内。

**结论：可行**。白天正常光线下，和系统相机的差距主要在多帧合成带来的动态范围和暗部噪点，
姿势照片这个场景（人站定、光线通常不差）差距可以接受。

### 2.5 其他路线

| 路线 | 结论 |
| --- | --- |
| 厂商开放能力（华为 Camera Kit / 小米） | 没有「把浮层盖到系统相机上」这种能力，且都是各自生态内的 SDK，跨厂商不可用 |
| Android 15 / 16 新 API | 没有解决这个问题的 API。Android 16 只是在 Camera2 里加了 hybrid AE（`about/versions/16/features`） |
| MediaPipe Android 原生版（`com.google.mediapipe:tasks-vision`） | 有，`PoseLandmarker` 可直接跑。代价是 ~20MB 的 AAR + `.task` 模型，且要自己写 YUV→Bitmap 的转换。**这是 A 路线做完整功能时绕不开的一块** |
| 半透明 WebView 复用现有 JS 管线 | 技术上可行（把 Camera2 的帧塞进一个隐藏 WebView 跑现有 MediaPipe 代码），但要自己做帧桥接，复杂度和直接上 MediaPipe 原生版差不多，不推荐 |

## 4. 推荐方案

### 4.1 主方案：A（自建 Camera2 预览 + 原生叠加）

**形态**：新增一个「原生拍摄模式」Activity，全屏 Camera2 预览，指导层用 Canvas 画在上面，
快门直接走 `TEMPLATE_STILL_CAPTURE` 出全分辨率 JPEG。网页端完全不动，作为「轻量模式」保留。

**为什么选它**：

1. 不依赖任何我们控制不了的外部条件（不用管系统相机是否 secure、不用管 ROM 给不给悬浮窗权限）
2. 权限只要 `CAMERA`，用户零学习成本
3. 预览和叠加在同一个 Surface 上，剪影对齐没有额外误差
4. 上架无风险

### 4.2 为什么不是 B

B 的画质确实更好，但它把产品的可用性押在两个不确定上：

- 系统相机是否 `FLAG_SECURE`（换台手机可能就废）
- 用户是否愿意每次拍照前点一次录屏授权（体验上是硬伤）

**而且 B 的"更好"是有限的**：用户真正抱怨的是"竖屏裁切后只剩 500px 宽"，A 直接给 4000px 宽。
从 500 到 4000 是质变，从 4000 到 4000+多帧 HDR 是量变。**先解决质变。**

### 4.3 风险

| 风险 | 应对 |
| --- | --- |
| 相机 UI 要重写（变焦、对焦、闪光灯、前后摄切换） | 第一版只做：预览 + 叠加 + 快门 + 前后摄切换。变焦用双指缩放，够用 |
| MediaPipe 原生版 20MB + 模型，APK 体积翻倍 | 模型放 assets，或用 `tasks-vision` 的 CPU 版；体积换功能，值得 |
| 部分机型预览 + 全分辨率 JPEG 组合不支持 | 原型里已有退化逻辑（只预览），正式版应改为「先试组合，失败就降到中等 JPEG」 |
| 厂商多帧算法缺失，暗光画质明显不如系统相机 | 暗光场景提示用户「用系统相机拍」，保留现有跳转入口作为兜底 |

### 4.4 回退方案

如果 A 的工程量评估下来太大（要重写相机 UI + 接 MediaPipe），**回退到现状**：
快门仍然跳系统相机，但把姿势指导提前——用户在网页上把姿势选好、记住，再跳过去按快门。
这是当前已经在做的事，成本为零。

**不要回退到 C**：只有悬浮窗、剪影不能贴合，等于把产品最核心的东西丢了。

### 4.5 如果一定要做 B，先做这三件事

1. 用原型按钮 2 在目标机型上实测是否全黑（至少覆盖华为/小米/OPPO/vivo 各一台）
2. 确认「每次弹录屏授权」这个体验能否被用户接受（大概率不能）
3. 想清楚锁屏、切后台、状态栏提示条这些边界

## 5. 原型说明

代码在 `android/app/src/main/java/cn/photocoach/app/probe/`，**完全独立**：

- 单独的 launcher 图标「原生叠加验证」，`MainActivity` 一行没改
- 零新增依赖，只用平台 API
- 验证完可以直接删掉 `probe/` 整个包 + manifest 里那三条权限和三个组件

| 文件 | 作用 |
| --- | --- |
| `OverlayProbeActivity.java` | 验证入口，四个按钮 |
| `ProbeOverlayService.java` | 悬浮窗 + MediaProjection 采样，把「有画面/全黑」写在浮层顶部 |
| `Camera2ProbeActivity.java` | Camera2 预览 + 叠加层 + 全分辨率 JPEG 拍照 |
| `GuideOverlayView.java` | 两边共用的叠加绘制（三分线 + 人形轮廓 + 状态行） |

**怎么跑**：

1. 装 APK，桌面会出现第二个图标「原生叠加验证」
2. 点 **1** → 授权「显示在其他应用上层」→ 浮层出现
3. 点 **2** → 系统弹录屏授权 → 同意 → **按 Home 切到系统相机**
4. 看浮层顶部那行字：
   - `录屏 有画面｜均值 xx` → 这台机器的系统相机**可以**被录，B 路线在它上面成立
   - `录屏 疑似全黑｜均值 0` → 系统相机打了 `FLAG_SECURE`，B 路线在这台机器上**不成立**
5. 点 **3** → 看 Camera2 自建预览的画质，底部会显示最大 JPEG 尺寸（这个数字就是 A 路线的画质上限）
6. 点「拍一张」→ 存到 `Android/data/cn.photocoach.app/files/probe/`，可用 `adb pull` 拉出来看

**浮层的状态行故意加了 `FLAG_SECURE`**，所以它不会出现在录屏结果里 —— 否则检测器看到的是
自己画的剪影，永远"有画面"。

**本地编译注意**：工程路径 `J:\project\拍照指导` 含中文，AGP 会直接报
`Your project path contains non-ASCII characters`。验证时是把 `android/` 整个复制到纯 ASCII 路径
下编译的。CI 跑在 Linux 的 ASCII 路径上，不受影响。

## 7. 一句话总结

**推荐 A：自建 Camera2 预览 + 原生叠加。** 它是唯一不依赖外部条件（系统相机是否允许录屏、
ROM 给不给悬浮窗权限）的方案，画质从 500px 宽直接跳到全分辨率，代价是要重写相机 UI、
缺厂商多帧算法。**最大的坑**：B 路线看着最省事（画质直接是设备上限），但它把可用性押在
「系统相机预览不是 `FLAG_SECURE`」上——这件事没有任何官方保证，换台手机就可能失效。
